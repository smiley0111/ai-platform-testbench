# ai-platform-testbench

AI 平台测试工作台。按 AI 开发平台的四大场景组织测试：模型 API、模型推理、模型训练、Notebook。

被测对象是一个自己写的 **OpenAI 兼容推理网关**，后端可以接本地 Ollama（真实模型），也可以接一个
**能注入故障的 Mock 后端**。可靠性测试（重试、超时、熔断、降级）必须能稳定复现故障，真实模型做不到，
所以默认用 Mock 跑，真实模型的用例单独标记。

## 运行

```bash
uv sync --extra dev
uv run pytest                 # 全部用例，Mock 后端
uv run pytest -m "not ollama" # 只跑不依赖真实模型的用例
uv run pytest -m "not training" # 跳过训练用例（每次训练都要起进程加载 torch，约 3 分钟）
uv run pytest -n 4            # 并行跑（pytest-xdist）
```

`uv sync` 下载很慢时，可以直接用已装好依赖的系统 Python：`python -m pytest`。
训练用例需要 `uv sync --extra train`（CPU 版 PyTorch 即可），没装 torch 时自动跳过。

启动网关（默认 Mock 后端，开发用 key 为 `sk-local-dev`）：

```bash
uv run python -m testbench.gateway.app
```

接 Ollama：

```bash
ollama pull qwen2.5:0.5b
TESTBENCH_BACKEND=ollama uv run python -m testbench.gateway.app
```

AI 生成用例评测（需要 Ollama 和对应模型；生成结果会缓存，重跑只重新执行和打分）：

```bash
uv run python -m testbench.aitest.evaluate
uv run python -m testbench.aitest.evaluate --runs qwen2.5:1.5b/schema --force
```

AI 生成用例评测（需要 Ollama 和对应模型；生成结果会缓存，重跑只重新执行和打分）：

```bash
uv run python -m testbench.aitest.evaluate
uv run python -m testbench.aitest.evaluate --runs qwen2.5:1.5b/schema --force
```

## 网关做了什么

请求依次经过：

1. **鉴权**：`Authorization: Bearer <key>`，缺失或错误返回 401
2. **限流**：每个 key 一个令牌桶，超出返回 429 和 `Retry-After`
3. **参数校验**：字段和取值范围对齐 OpenAI，错误返回 400，`param` 指出是哪个字段
4. **模型权限（RBAC）**：key 只能访问被授权的模型，否则 403
5. **内容过滤**：输入命中拦截词返回 400；输出命中则打码，`finish_reason` 置为 `content_filter`
6. **重试 / 超时**：后端 5xx 和 429 指数退避重试，4xx 不重试；超时返回 504
7. **熔断**：连续失败达到阈值后打开，快速返回 503；一段时间后半开，放一个试探请求
8. **降级**：主模型失败或熔断时切到备用模型，响应头 `x-fallback: true`、`x-served-model` 标明实际模型

所有错误都是 OpenAI 的格式 `{"error": {"message", "type", "param", "code"}}`，官方 SDK 能识别成对应的异常类型。

## 测试设计

### 阶段 1：模型 API

| 文件 | 测什么 | 关键用例 |
| --- | --- | --- |
| `test_functional.py` | 功能正确性 | 响应结构；usage 求和；多轮对话；`max_tokens` 截断与 `finish_reason=length`；`stop`；11 种非法参数；边界值；多模态输入；Embeddings 顺序、维度、确定性 |
| `test_streaming.py` | 流式 SSE | 事件格式与 `[DONE]`；所有 chunk 同一个 id；流式拼接结果等于非流式；`include_usage`；**中途断流不能发 `[DONE]`**；首包前失败可重试 |
| `test_compat.py` | 协议兼容 | 官方 `openai` SDK 只改 `base_url` 就能调用对话、流式、Embeddings、模型列表；401/403/404/400/429 被 SDK 识别成正确的异常类 |
| `test_security.py` | 安全性 | 5 种鉴权失败；**鉴权先于参数校验**；错误信息不回显 key；RBAC；限流按 key 隔离；**非法请求也消耗配额**；输入、多模态、输出、流式输出的内容过滤 |
| `test_reliability.py` | 可靠性 | 瞬时错误重试成功；超过次数放弃；4xx 不重试；超时按时返回；熔断打开后快速失败且不再打后端；半开成功恢复、失败重新打开；熔断按模型隔离；降级与流式降级；50 个并发请求 |

几个值得注意的设计点（也是用例里的断言）：

- **中途断流时不能发 `[DONE]`。** 否则客户端会把半截回答当成完整回答展示给用户。
- **鉴权和限流在参数校验之前。** 否则未授权的人能探测接口行为，攻击者也能用错误请求无限刷接口。
- **降级要如实告诉用户。** 响应里的 `model` 字段和响应头都要标明实际是哪个模型回答的。
- **测试里关掉 SDK 的自动重试。** `openai` SDK 默认对 429 和 5xx 自动重试 2 次，不关掉就测不到网关的真实行为。

### 阶段 2：性能基准

```bash
pip install locust
python perf/run_benchmark.py            # 完整跑约 8 分钟，生成 reports/perf-report.md
python perf/run_benchmark.py --quick    # 每档 15 秒，验证脚本用
python perf/run_benchmark.py --report-only  # 不压测，用上次的原始数据重新出报告
```

`perf/locustfile.py` 是压测用户，`perf/run_benchmark.py` 负责起网关、调度场景、汇总出报告。

| 场景 | 怎么测 | 看什么 |
| --- | --- | --- |
| 冷启动 vs 热启动 | 用 Ollama 的 `keep_alive: 0` 卸载模型后发单请求，再连发热请求 | 首 token 时延差多少倍 |
| 阶梯并发 | 1/2/4/8/16 并发闭环压测，每档 60 秒 | 吞吐（token/s、TPM）在哪一档到顶，首 token p95 怎么涨；用 Little 定律校验 |
| 负载下限流 | `rpm=12` 的 key，8 并发 | 实测放行数是否等于令牌桶理论值（容量 + 回填 × 时长），429 是否足够快 |
| 负载下超时 | 网关超时 1.5 秒，16 并发 | 504 的实际等待时间、是否触发熔断、压后能否恢复 |

压测方法上的几个选择：

- **首 token 时延（TTFT）和端到端时延分开统计。** 流式接口用户感知的是首 token，只看端到端会掩盖排队问题。
- **输出长度固定。** 提示词要求长回答、`max_tokens=64`、`temperature=0`，保证每次都生成满 64 个 token，不同并发档之间才可比。
- **吞吐用后端返回的 `usage.completion_tokens` 计算**，而不是数 chunk。
- **客户端出错后退避**（遵守 `Retry-After`，否则等 1 秒），和真实 SDK 行为一致；否则 429/503 会在闭环里空转，把计数刷爆。
- **网关和 Locust 分两个进程。** Locust 依赖 gevent 打补丁，和 uvicorn 放在一个进程会互相干扰。

### 阶段 3：训练

被测对象是 `src/testbench/training/trainer.py`，一个故意做小的训练框架：合成数据、带 Dropout 的 MLP、
带动量的 SGD，CPU 上几秒跑完。它具备真实训练任务的关键机制：gloo 数据并行、定期 Checkpoint、
自动从最新存档恢复、指标写 JSONL 和 TensorBoard。还内置了故障注入：在第 N 步杀进程、写存档写到一半时退出、
只杀某一个 rank。

```bash
python -m testbench.training.trainer --out runs/demo --world-size 2 --crash-at-step 25  # 第 25 步被杀
python -m testbench.training.trainer --out runs/demo --world-size 2                     # 自动从第 20 步恢复
```

| 文件 | 测什么 | 关键用例 |
| --- | --- | --- |
| `test_training.py` | 训练正确性 | loss 下降；同种子两次训练逐位一致；数据并行（2 进程）与单进程等价；各 rank 参数一致；TensorBoard 标量与日志一致 |
| `test_checkpoint.py` | 断点续训与容错 | 被杀后恢复与不中断训练**逐位一致**；恢复后日志无重复步；写存档时崩溃不留坏存档；存档损坏退回上一个；旧存档清理；单个 rank 崩溃时整个作业快速失败不挂起；多进程恢复；2 进程中断后用 1 进程接着训 |

测试思路：

- **用“和不中断训练的结果一致”判断恢复是否正确**，不能只看“能恢复、loss 在降”。随机数状态、
  优化器动量、数据读到第几批，任何一个没恢复，训练都能继续跑，loss 也照样下降，只是结果悄悄偏离了。
- **每个“一致”都配一个反例对照**。例如故意不恢复随机数状态或优化器状态，断言结果**必须**偏离；
  故意把批大小切错，断言和单进程**必须**不同。否则无法区分“真的正确”和“测试太松、怎样都能过”。
- **数据并行只能近似相等**。两个进程各算一半再求平均，和单进程算整批在数学上等价，但浮点求和顺序不同，
  实测参数差约 1e-7；容差设 1e-5，切分或平均写错时误差会大好几个数量级。
- **存档要原子写入**。先写到 `.tmp` 目录，全部写完再改名；读取时忽略 `.tmp`，文件损坏就退回上一个。
- **数据顺序只由（种子，步数）决定**。单进程也用 `num_replicas=1` 的 `DistributedSampler`，
  所以换进程数恢复时，每一步取到的样本集合不变。

### 阶段 4：Notebook

被测对象是 `src/testbench/notebook/service.py` 里的 `NotebookService`，相当于 AI 平台 Notebook 后端的最小实现：
用 `jupyter_client` 替用户启动和管理真实的 ipykernel 内核，负责执行超时、崩溃恢复、内存和输出限制、用户配额、空闲回收，
以及整本 Notebook 的批量执行（定时任务场景）。

| 文件 | 测什么 | 关键用例 |
| --- | --- | --- |
| `test_execution.py` | 执行与输出 | 返回值与执行计数；跨单元状态保持；stdout/stderr 分流；富文本输出；中文；运行时错误和语法错误后内核可用；**输出刷屏被截断** |
| `test_lifecycle.py` | 生命周期与多用户 | 重启清空状态并换进程；**关闭后进程退出、连接文件删除**；关闭的会话拒绝访问；会话隔离；不同内核并行、同一内核排队；用户配额；空闲回收不误杀正在执行的内核 |
| `test_faults.py` | 异常与资源限制 | 超时中断后状态保留；**用户代码吞掉中断时升级为重启**；C 层阻塞调用的等待有上限；停止按钮；**内核崩溃自动恢复**并保留崩溃前的输出；**内存超限重启**；连续故障后服务正常 |
| `test_run_notebook.py` | 整本执行 | 输出写回且文件合法；遇错即停；允许出错继续；单元超时 |

整轮测试结束时，夹具检查本进程下没有残留的 ipykernel 子进程。孤儿内核是 Notebook 平台最常见的资源泄漏。

测试中的几个发现：

- **Windows 上中断打不断阻塞在 C 层的调用。** ipykernel 在 Windows 上用 `_thread.interrupt_main()` 实现中断，
  它只在解释器执行 Python 字节码时生效，所以 `time.sleep(60)` 要等它返回才会被中断；Linux 上用的是真实信号，会立即打断。
  平台不能依赖中断一定生效，必须有“宽限期过后强制重启”的兜底。用例只断言等待时间有上限、内核随后可用，不绑定具体走哪条路径。
- **重启要明确告诉用户状态丢了。** 超时升级、崩溃、内存超限都会重启内核，`ExecResult.restarted` 为真；
  用例同时断言之前定义的变量确实不在了，确保这个标记不是摆设。
- **stdout 和 stderr 之间的先后顺序没有保证。** 两个流各自缓冲，只能断言各自的内容。
- **健康检查要按时间触发。** 如果只在“没收到消息时”检查内存和存活，代码一边刷输出一边吃内存时永远轮不到检查。

### 阶段 5：AI 辅助测试

让本地小模型读 [`api_spec.md`](src/testbench/aitest/api_spec.md)（网关的接口文档），按 5 个类别生成测试用例，
再用一套和模型无关的指标评价这些用例到底有多少用。结果见 [AI 生成用例评测报告](reports/aitest-report.md)。

用例是 JSON 数据而不是代码：模型只描述“发什么请求、期望什么状态码和错误码”，由 `runner.py` 统一执行。
这样模型写不出能跑但什么都没测的代码，评测也能逐条归因。

| 模块 | 作用 |
| --- | --- |
| `cases.py` | 用例的 JSON Schema、解析与格式校验 |
| `runner.py` | 对网关逐条执行用例，判断通过与否 |
| `generate.py` | 调 Ollama 生成用例；可选约束解码（`format` 传 JSON Schema）或自由输出 |
| `requirements.py` | 从接口文档整理出的 26 条需求，用于统计需求覆盖 |
| `mutation.py` | 14 个植入的 bug（变异体），每个在源码副本上用子进程跑一遍用例 |
| `evaluate.py` | 汇总指标，写报告 |

评价指标：

- **格式不合法、重复**：解析不了或语义不成立（例如 GET 带请求体）的用例，以及同一请求重复出现的用例。
- **有效率**：在正确的网关上执行，期望和实际一致的比例。期望写错的用例要么是模型理解错了文档，要么是网关有 bug，需要人工判断。
- **需求覆盖**：有效用例覆盖了 26 条需求中的多少条。
- **变异得分**：植入的 14 个 bug 里，有多少个能被这套用例发现。这是最接近“测试有没有用”的指标，覆盖到了不等于测出来了。

评测框架自身先用 30 条人工编写的用例验证：有效率 100%、需求覆盖 26/26、变异得分 14/14；
同时用一套只测成功路径的弱用例做反向对照，它最多只能杀死 1 个变异体，说明变异得分能区分好坏用例。

实测结果（温度 0、固定种子、CPU 推理）：

| 来源 | 有效率 | 需求覆盖 | 变异得分 |
| --- | --- | --- | --- |
| 人工编写 | 100% | 26/26 | 14/14 |
| qwen2.5:0.5b 约束解码 | 35% | 1/26 | 1/14 |
| qwen2.5:1.5b 约束解码 | 83% | 11/26 | 7/14 |
| qwen2.5:1.5b 自由输出 | 57% | 9/26 | 5/14 |
| qwen2.5:3b 约束解码 | 62% | 9/26 | 3/14 |

几个发现：

- **约束解码只保证格式，不保证内容。** 最初 Schema 里 `body` 是可选字段，模型在约束下干脆全部省略，每条请求都变成空请求体；
  改成必填后，模型又改填 `null`。3b 模型 38 条用例里有 22 条是“名字叫缺少 messages、请求体却是 null”，
  测试意图只写在名字里，没有落到数据上。
- **模型越大不一定越好。** 3b 的格式错误集中在上面这一种模式，扣掉之后剩下的用例质量并不差；
  换一种 Schema 或提示词，排名可能就变了。比较模型时必须固定提示词和 Schema，并且看错误的分布，而不是只看一个总分。
- **小模型最容易错在校验顺序上。** 网关先校验参数、再做内容过滤和模型检查。0.5b 照抄示例里的 `temperature: 3`，
  导致本该测内容过滤和模型权限的用例全部先被参数校验拦下，期望错误码对不上。
  这类错误不是格式问题，只有执行之后才看得出来。
- **需求覆盖高估了用例的作用。** 1.5b 覆盖了 42% 的需求，但只杀死了 50% 的变异体；
  边界值（`max_tokens` 上限差一、`top_p` 上界）这类 bug，几乎没有模型生成的用例能发现。
- **生成的用例不能直接当回归用例。** 期望和实际不一致时，可能是模型错了，也可能是网关真有 bug；
  如果把实际结果回填成期望，就等于把 bug 固化进用例。比较稳妥的用法是让模型补充思路、人工审核后入库。

### 已知限制

- 流式输出的内容过滤按 chunk 检查，拦截词如果被切在两个 chunk 之间会漏掉。真实系统需要维护一个滑动窗口缓冲。
- Mock 后端按空格切分 token，只用于验证网关逻辑，不代表真实模型的 token 计数。
- 性能数据来自 CPU 推理的 0.5B 模型，压测客户端和模型在同一台机器上，只能说明测试方法，绝对数值不代表 GPU 推理服务。
- 流式请求的超时只约束首个 chunk，生成过程中卡住不会触发超时。
- 训练场景只在单机 CPU 上用 gloo 模拟数据并行，没有覆盖 GPU/NCCL、多机网络、模型并行和混合精度。
- 换进程数恢复时，各 rank 的随机数状态无法一一对应，只能重新播种，所以带 Dropout 时无法和原训练逐位一致。
- Notebook 的内存限制是服务端轮询内核进程的 RSS（每 0.1 秒一次），瞬间的内存尖峰可能漏检；生产环境应由 cgroup 或容器限制兜底。
- Notebook 服务是进程内的 Python API，没有做 HTTP/WebSocket 接口和鉴权，这部分在阶段 1 的网关里已经覆盖了测试方法。
- AI 生成用例只评测了 3B 以下的本地模型、一版提示词和一次采样（温度 0），结论只说明评测方法，不代表大模型的上限。
